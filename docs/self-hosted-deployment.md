# راه‌اندازی مستقل IdeaApp Builder

این راهنما برنامه و Worker را برای استقرار مستقل آماده می‌کند؛ آن را به معنی انتقال انجام‌شده یا قطع سرویس قبلی ندانید. دیتابیس موجود Neon را با همان URL و همان کلیدهای رمزنگاری و نشست نگه دارید. هیچ کلید یا اطلاعات ورود را در مخزن یا لاگ قرار ندهید.

## پیش‌نیازها و ارزیابی

- پیش از نصب، منابع VPS، دیسک، سرویس‌های فعال، مسیرهای Caddy/Nginx و نسخه Node و Docker را فقط‌خواندنی بررسی کنید. روی VPS دارای EPC بدون بررسی ظرفیت و ایزولاسیون تغییر ایجاد نکنید.
- Node 22 و PostgreSQL 17 یا Neon؛ URL دیتابیس موجود و کلیدهای محیط فعلی را به‌صورت امن منتقل کنید. نصب Worker به ابزار توسعه `tsx` نیز نیاز دارد؛ از `npm ci` کامل در محیط Worker استفاده کنید.
- Worker به daemon محلی Docker و همان فایل‌سیستم میزبان نیاز دارد؛ Docker socket از نظر امنیتی عملاً دسترسی ریشه است. Worker باید در ماشین یا VM جداگانه با Docker اختصاصی، بدون داده‌های EPC و اسرار وب‌سرور، اجرا شود. استفاده از Docker روی همان VPS مشترک بدون ارزیابی جداسازی مناسب نیست.
- پیش از cutover از دیتابیس نسخه پشتیبان تهیه کنید و بازیابی را روی محیط جداگانه امتحان کنید. Migrationهای لازم را ابتدا روی کپی آزمایشی هم‌نسخه Production با ابزار موجود و اتصال مستقیم آزمایش کنید؛ `db:push` جایگزین Migration نیست.

## آماده‌سازی نسخه

روی میزبان وب در دایرکتوری نسخهٔ تازه و جداگانه، بعد از تنظیم متغیرها در فایلی محدود به حساب سرویس:

```bash
npm ci
npm run typecheck
npm test
npm run build:selfhost
```

از checkout تازه استفاده کنید: نسخه قبلی Workflow ممکن است فایل‌های تولیدی نادیده‌گرفته‌شده را زیر `src/app/.well-known/workflow/v1` به جا گذاشته باشد و در build جدید خطا بدهد. این مسیر را در checkout کاری دارای فایل سفارشی، بدون بررسی حذف نکنید.

دستور آخر خروجی Next.js standalone به همراه فایل‌های ایستا را می‌سازد. واحد نمونه `deploy/systemd/ideaapp-web.service` فرض می‌کند نسخه در `/opt/ideaapp/current` و تنظیمات در `/etc/ideaapp/web.env` است. مجوز خواندن این فایل را فقط به سرویس مربوط بدهید. در صورت نیاز، `CRON_SECRET` برای endpoint گزارش صف به صورت اختیاری تنظیم می‌شود. پورت `3100` روی VPS موجود اشغال است و خود سرویس `moradi-ideaapp.service` نیز از قبل اجرا می‌شود. نمونهٔ واحد از پورت `3310` استفاده می‌کند، اما آزاد بودن آن هنوز بررسی نشده است؛ پیش از استفاده با `ss -lnt` بررسی کنید و تنظیم واقعی سرویس موجود را تطبیق دهید. هیچ واحد جدیدی را هم‌زمان روی پورت سرویس موجود شروع نکنید. Reverse proxy باید پس از آزمون، به پورت تأییدشده هدایت شود و TLS را مدیریت کند؛ تنظیمات EPC را بازنویسی نکنید.

روی میزبان Worker همان commit و `npm ci`، متغیرهای ضروری در `/etc/ideaapp/worker.env`، سپس تصاویر `worker/Build.Dockerfile`، `worker/Dockerfile` و `postgres:17-alpine` را طبق [راهنمای ایجنت](agentic-workflows.md) آماده کنید. واحد `deploy/systemd/ideaapp-worker.service` صرفاً نمونه است و گروه Docker آن اختیار ریشه دارد؛ برای میزبان مشترک تأیید امنیتی کافی نیست. Web و Worker باید دیتابیس و کلید رمزنگاری یکسان داشته باشند؛ متغیرهای سرویس‌ها را به اندازه نیاز محدود کنید.

## پیش از تغییر مسیر عمومی

1. روی مسیر یا زیردامنه Staging اختصاصی، بدون دستکاری DNS اصلی، لاگین GitHub و ایمیل، پرداخت آزمایشی، نمایش پروژه، صف و یک اجرای بدون API پولی را تست کنید. کد صحت OTP، secret و توکن را در گزارش ننویسید.
2. `APP_URL` باید همان مبدأ عمومی نهایی باشد. در GitHub OAuth App، `https://ideaapp.anzanagenticai.ir/api/auth/github/callback` را در صورت استفاده از این دامنه ثبت کنید و در Google/درگاه پرداخت نیز آدرس‌های بازگشت همان مبدأ را هماهنگ کنید. تست ورود به تنظیمات واقعی OAuth وابسته است.
3. نرخ‌ها و سقف مصرف AI، هزینه‌های قبلی بدون قیمت و migrationهای Production را بررسی کنید. Migrationهای موجود از 0008 تا 0012 در زمان تدوین راهنما هنوز روی کپی Production تأیید نشده‌اند. این موضوع می‌تواند درخواست AI کلید مرکزی را متوقف کند.
4. صف منتظر را بررسی کنید؛ Worker جدید را پیش از تغییر مسیر فقط با برنامه مشخص و بدون اجرای هم‌زمان Worker قدیمی فعال کنید. اجرای آزمایشی از سرویس‌های مالی یا AI واقعی استفاده نکند.
5. پس از موفقیت تست‌ها، با طرح بازگشت مشخص DNS یا reverse proxy را تغییر دهید و لاگ‌ها و `/api/health` را کنترل کنید. سلامت HTTP به‌تنهایی به معنی کارکرد Worker و OAuth نیست.

## بازگشت

DNS و مقصد proxy قبلی و فایل‌های استقرار قبلی را نگه دارید. در صورت شکست، ترافیک را به مقصد قبلی بازگردانید و Worker جدید را متوقف کنید تا صف توسط دو runtime ناسازگار اجرا نشود. Migration افزایشی را بدون برنامه بازگشت معتبر حذف نکنید و هیچ سرویس قدیمی را تا تأیید پایداری حذف نکنید.
