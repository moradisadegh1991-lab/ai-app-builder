# ساخت پروژه با تیم تخصصی هوش مصنوعی

این مسیر جایگزین تولید یک‌مرحله‌ای شده است. API درخواست را در PostgreSQL ثبت می‌کند و با وضعیت `202` پاسخ می‌دهد. یک Worker مستقل، کار را تا پایان ادامه می‌دهد؛ بستن مرورگر اجرای تیم را متوقف نمی‌کند.

## نقش‌ها و ترتیب اجرا

1. **معمار** نیازمندی یا قرارداد مشترک ماژول‌ها، API و مسیرهای قابل‌آزمایش کاربر را می‌سازد.
2. **طراح UI/UX** توکن‌های طراحی، کامپوننت‌ها، چیدمان موبایل و دسکتاپ، RTL، دسترس‌پذیری و حالت‌های خالی/خطا/بارگذاری/موفقیت را مشخص می‌کند.
3. **Frontend و Backend** پس از آماده‌شدن قراردادها، موازی کار می‌کنند. مالکیت مسیرها جداست؛ فایل‌های قالب همچنان قفل هستند.
4. **ابزار ارزیابی** TypeScript و build را اجرا می‌کند. برای وب و Capacitor، برنامه در مرورگر واقعی با اندازه موبایل و دسکتاپ باز می‌شود و مسیرهای کاربر آزمایش می‌شوند.
5. **ارزیاب مستقل** کد، قراردادها، نتیجه ابزارها و اسکرین‌شات‌ها را بررسی می‌کند.
6. **متخصص رفع خطا** مشکلات مشخص را اصلاح می‌کند. ابزارها و ارزیاب دوباره اجرا می‌شوند؛ حداکثر دو دور اصلاح انجام می‌شود.

فقط وقتی بررسی ابزارها موفق است و مشکل مسدودکننده‌ای در گزارش ارزیاب نیست، نسخه جدید ذخیره می‌شود. خطای زیرساخت باعث بازنویسی بی‌دلیل کد نمی‌شود. نسخه قبلی تا تأیید نسخه جدید قابل استفاده می‌ماند. ویرایش و اصلاح پروژه‌ای که به GitHub وصل است، پس از تأیید کیفیت به GitHub فرستاده می‌شود؛ اگر ارسال شکست بخورد کد تأییدشده باقی می‌ماند و دکمه ارسال قابل استفاده است.

برای Expo، TypeScript و Metro Android export بررسی می‌شوند. **اجرای APK و بررسی بصری اندروید به شبیه‌ساز نیاز دارد و در این Worker انجام نمی‌شود.** گزارش این بخش را صریحاً «انجام نشده» نشان می‌دهد. ساخت APK همچنان از GitHub Actions انجام می‌شود.

## راه‌اندازی

پیش‌نیاز: Node.js 22، PostgreSQL، Docker محلی روی میزبان Worker، حداقل حدود 8GB فضای آزاد برای ساخت تصویرها و کانتینرهای موقت. Worker باید از ریشه همین checkout اجرا شود؛ Docker daemon و Worker باید فایل‌سیستم میزبان مشترک داشته باشند. از Docker daemon اختصاصی Worker استفاده کنید.

روی دیتابیس جدید:

```bash
npm ci
cp .env.example .env.local
# DATABASE_URL و کلیدهای لازم را در فایل وارد کنید.
npm run db:migrate
```

اگر دیتابیس قبلی را با فایل `all-in-one.sql` نسخه قدیمی یا `db:push` ساخته‌اید و migrationهای `0000` تا `0005` واقعاً اعمال شده‌اند:

```bash
npm run db:migrate -- --baseline-through 0005_rate_limits
```

این گزینه فقط migrationهای قبلی را ثبت‌شده فرض می‌کند؛ پیش از استفاده، موجودبودن همان schema را بررسی کنید. برای نصب دارای جدول استاندارد `drizzle.__drizzle_migrations`، دستور معمولی کافی است. گزینه دیگر اجرای مستقیم فایل‌های `0006_agentic_workflows.sql` و `0007_atomic_usage_and_payments.sql` روی دیتابیس فعلی است.

`db:push` به‌تنهایی برای نصب کامل کافی نیست: تابع‌های اتمیک رزرو مصرف و پرداخت نیز باید از migrationها نصب شوند. فایل تازه `drizzle/all-in-one.sql` همه تغییرات را برای دیتابیس خالی دارد. `/api/health` وجود جدول‌ها، ستون‌ها و تابع‌های جدید را بررسی می‌کند.

روی میزبان Worker:

```bash
docker build -f worker/Build.Dockerfile -t idea2app-build:1 worker
docker build -t idea2app-sandbox:1 worker
docker pull postgres:17-alpine
npm run worker
```

برای محیط دارای CA اختصاصی پراکسی، ساخت تصویر مرورگر از `--secret id=proxy_ca,src=/path/to/ca.pem` پشتیبانی می‌کند. `AGENT_NPM_CA_FILE=/path/to/ca.pem` همان CA را فقط در مرحله نصب وابستگی‌های نمونه به‌صورت read-only در کانتینر قرار می‌دهد. اعتبارسنجی TLS را غیرفعال نکنید.

وب‌سرور با `npm run dev` یا روش معمول Vercel اجرا می‌شود. **Worker یک پردازش دائم روی VPS/میزبان دارای Docker است و داخل Route Handler یا تابع کوتاه‌عمر Vercel اجرا نمی‌شود.** هر دو باید `DATABASE_URL`، کلید رمزنگاری و کلیدهای AI یکسان داشته باشند. برای اجرای دائم می‌توان از systemd یا مدیر پردازش میزبان استفاده کرد. `SIGTERM` کار جاری را قطع می‌کند؛ Worker بعدی پس از انقضای lease آن را بازیابی می‌کند.

نمونه واحد systemd (مسیرها را با نصب خودتان تطبیق دهید):

```ini
[Unit]
Description=Idea2App specialist worker
After=network-online.target docker.service
Requires=docker.service

[Service]
User=idea2app-worker
SupplementaryGroups=docker
WorkingDirectory=/opt/ai-app-builder
ExecStart=/usr/bin/node --env-file=.env.local --import tsx scripts/agent-worker.ts
Restart=always
RestartSec=5
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target
```

## انتخاب مدل هر متخصص

ارائه‌دهنده انتخاب‌شده در صفحه پروژه پیش‌فرض تیم است. متغیرهای سرور می‌توانند برای هر نقش ارائه‌دهنده و مدل جدا تعیین کنند:

```dotenv
AGENT_ARCHITECT_PROVIDER=openai
AGENT_DESIGNER_PROVIDER=gemini
AGENT_FRONTEND_PROVIDER=anthropic
AGENT_BACKEND_PROVIDER=openai
AGENT_REVIEWER_PROVIDER=gemini
AGENT_DEBUGGER_PROVIDER=anthropic
```

برای هر نقش می‌توان `AGENT_<ROLE>_MODEL` و `AGENT_<ROLE>_ECONOMY_MODEL` را هم تعیین کرد. مدل اقتصادی برای کلید مرکزی کاربران رایگان حفظ می‌شود. اگر کلید ارائه‌دهنده یک نقش تنظیم نشده باشد، اجرا با خطای روشن متوقف می‌شود؛ مدل گران‌تر به‌صورت پنهانی جایگزین نمی‌شود. انتخاب مدل باید با پشتیبانی بینایی و سقف خروجی API سازگار باشد.

## ماندگاری، بودجه و خطا

- `workflow_runs`: صف، وضعیت اجرا، مالک و lease، سقف بودجه.
- `agent_tasks`: نقش، hash ورودی و خروجی نسخه‌دار هر مرحله؛ خروجی‌های موفق هنگام بازیابی دوباره مصرف AI ایجاد نمی‌کنند. قرارداد طراحی و API نیز همین‌جا ذخیره می‌شوند.
- `evaluations`: نتیجه ابزار و ارزیاب در هر دور؛ تصاویر واقعی در خروجی مرحله verifier نگه داشته می‌شوند و فقط مالک پروژه می‌تواند دریافت کند.
- `usage_reservations`: رزرو اتمیک پیش از تماس با API؛ درخواست‌های هم‌زمان یک بودجه را دوبار خرج نمی‌کنند.

هر پروژه فقط یک اجرای فعال دارد. Worker هر 20 ثانیه lease دو‌دقیقه‌ای را تمدید می‌کند. Worker دارای مالکیت منقضی اجازه ذخیره نتیجه ندارد. بازیابی پردازش حداکثر سه بار انجام می‌شود؛ خطاهای معمول مدل/کیفیت به‌جای تکرار نامحدود، ثبت و متوقف می‌شوند. دکمه توقف در صفحه پروژه نیز وجود دارد.

`WORKFLOW_MAX_TOKENS` (پیش‌فرض 250000) مصرف کل هر اجرا را محدود می‌کند، حتی با کلید شخصی. سقف طرح کاربران کلید مرکزی علاوه بر آن اعمال می‌شود. رزرو ورودی بر اساس بایت UTF-8 محافظه‌کارانه است و پس از دریافت پاسخ، با مصرف واقعی ارائه‌دهنده تسویه می‌شود. در timeout/قطع پردازش، چون مصرف سمت ارائه‌دهنده نامعلوم است، رزرو نگه داشته می‌شود و در پنجره‌های مصرف به‌تدریج منقضی می‌شود. اجرای بازیابی‌شده ممکن است تماس قطع‌شده را دوباره ارسال کند؛ تضمین «دقیقاً یک تماس API» برای ارائه‌دهنده خارجی وجود ندارد.

کانتینر نصب وابستگی فقط manifest قالب را با lifecycle scriptهای غیرفعال نصب می‌کند. build و اجرای برنامه دسترسی به اینترنت و کلیدهای پلتفرم ندارند. پایگاه داده آزمایشی مستقل و موقت است؛ role برنامه superuser نیست. مرورگر در کانتینر دیگری اجرا می‌شود تا کد برنامه نتواند گزارش یا تست‌های آن را تغییر دهد. Docker socket به هیچ کانتینر آزمایش داده نمی‌شود. محدودیت حافظه، CPU، زمان و تعداد پردازش اعمال می‌شود. در محیط چندمستاجری با نیاز جداسازی قوی‌تر، میزبان Worker یا runtime کانتینر باید متناسب با آن انتخاب شود.

## بررسی بدون هزینه AI

```bash
npm run typecheck
npm test
npm run verify:sample
npm run verify:sample -- --backend
```

دو دستور آخر از قالب ثابت استفاده می‌کنند، AI را فراخوانی نمی‌کنند و تصاویر را در `out/agent-review/` می‌نویسند. نمونه بک‌اند ثبت و نمایش پیام را در مرورگر با PostgreSQL موقت بررسی می‌کند. تست‌های خودکار دیگر، قرارداد نقش‌ها، حلقه اصلاح، ممانعت از تحویل با build ناموفق، migrationها، صف، بازیابی مالکیت، رزرو مصرف و rollback پرداخت را پوشش می‌دهند.
