# ممیزی آمادگی درآمد و هزینه — اسپرینت ۱

مبنای ممیزی: مخزن IdeaApp Builder، سند `CODEX_HANDOFF_IDEAAPP_EPC_90D.md` و کد موجود. مبالغ صورتحساب و وضعیت عملیاتی درگاه‌ها تأیید نشده‌اند؛ اهداف سند پیش‌بینی درآمد نیستند.

## مسیرهای موجود

- هویت: `src/app/api/auth/` و `src/lib/session.ts`؛ سپس ایده و پرسش‌ها در `src/app/api/ai/idea-questions/route.ts`، مشخصات و تولید در `src/app/api/projects/[id]/`.
- صف و checkpoint در `src/lib/workflows/queue.ts`، worker در `src/lib/workflows/worker.ts` و تیم تخصصی در `src/lib/agents/orchestrator.ts`. معماری، طراحی، تولید موازی، ابزار، بازبینی و رفع محدود از قبل وجود دارند؛ حفظ شده‌اند. `docs/agentic-workflows.md` محدودیت‌های Sandbox و عدم آزمون APK در شبیه‌ساز را شرح می‌دهد.
- `src/lib/ai/index.ts` کلید شخصی را مقدم می‌کند، مدل اقتصادی را برای حساب رایگان انتخاب و قبل از درخواست رزرو توکن می‌کند. `providers.ts` gateway سازگار با OpenAI و Liara را پشتیبانی می‌کند. `liara-pricing.ts` نرخ تومانی مدیر و کاتالوگ عمومی دلاری را از هم جدا می‌کند؛ کاتالوگ صورت‌حساب نیست.
- `src/lib/billing/payments.ts` و مسیرهای checkout و callback زرین‌پال و Stripe را دارند. تابع `complete_payment` در migration 0007 فعال‌سازی تکراری را مهار می‌کند؛ جریان واقعی پرداخت و تسویه sandbox در این بررسی اجرا نشده است.
- `src/lib/pipeline.ts` پس از ارسال کد به GitHub، ساخت GitHub Actions را پیگیری و لینک APK/Artifact را بازیابی می‌کند. صورتحساب و دقیقه‌های منتسب به هر ساخت در این سیستم وجود ندارد. خود GitHub ممکن است سهمیه رایگان، نرخ سازمان یا صورتحساب متفاوت داشته باشد.

## ریسک و وضعیت

### P0 — پیش از فروش عمومی

1. **انجام‌نشده:** سقف پولی اتمیک روزانه/ماهانه پلتفرم، کاربر، پروژه و هر اجرا وجود ندارد. رزرو موجود فقط توکن است؛ تا تکمیل آن، پلتفرم در برابر افزایش قیمت مدل محافظت مالی قطعی ندارد.
2. **انجام‌شده به‌صورت محدود:** migration 0008 برای مصرف اندازه‌گیری‌شده، شناسه رزرو/اجرا، نقش، gateway و برآورد تومانی به همراه snapshot نرخ مدیر اضافه می‌کند. نرخ نامعتبر، قدیمی، مدل متفاوت، تصویر و کلید شخصی به شکل نامشخص ثبت می‌شوند. این تنها برآورد متن است، نه صورتحساب یا هزینه واقعی قطعی. مصرف بدون آمار معتبر همچنان رزرو محافظه‌کارانه دارد و سابقه برآوردی مستقل ایجاد نمی‌کند.
3. **انجام‌نشده:** هزینه و زمان هر build، سهم overhead و هزینه تحویل موفق به داده صورتحساب قابل استناد نیاز دارند. داده قدیمی و زمان‌های بدون قیمت را صفر فرض نکنید.
4. **انجام‌نشده:** طرح رایگان هنوز ۱۰۰ هزار توکن در ۵ ساعت، ۳۰۰ هزار در هفته و ساخت APK دارد. محدودکردن آن باید همراه سیاست اطلاع‌رسانی، حفظ اشتراک‌های خریداری‌شده، BYOK و سهمیه compute انجام شود.
5. ایزوله‌سازی Docker فعلی شامل محدودیت CPU/حافظه، حذف قابلیت‌ها و قطع شبکه در مراحل اجرای کد است (`src/lib/agents/sandbox.ts`). این بررسی ممیزی امنیتی کامل یا تأیید مناسب بودن هم‌مکانی با EPC نیست.

### P1/P2

- P1: گزارش فقط‌مدیر برای برآوردها، مغایرت با صورت‌حساب، درآمد وصول‌شده و حاشیه مشارکت؛ تکمیل پس از کنترل هزینه.
- P1: آزمون sandbox زرین‌پال و callback تکراری، جریان پرداخت واقعی و سیاست تحویل؛ هرکدام جداگانه تأیید شود.
- P2: ارزیابی شرایط استفاده Vercel و گزینه مهاجرت؛ بدون تغییر زیرساخت یا اتکا به فرض سرور مشترک.

## ترتیب اجرای باقیمانده

1. تعریف نرخ‌های مورد تأیید و منبع و تاریخ آن، سیاست تبدیل ارز و دوره جبران مصرف تاریخی نامعلوم؛ سپس طراحی رزرو اتمیک پولی سراسری با قفل تراکنشی، با پوشش parallel، retry، timeout، تغییر نرخ، BYOK و عدم کفایت موجودی. در نبود نرخ معتبر، درخواست با کلید پلتفرم باید با پیام عملی متوقف شود.
2. محدودیت مجزا و اتمیک build و تولید رایگان، بدون کاهش حق اشتراک خریداری‌شده؛ ثبت سیاست جدید و نحوه اطلاع‌رسانی.
3. اتصال هزینه build به اطلاعات قابل اتکای GitHub و مشخص‌کردن هزینه نامعلوم؛ بعد گزارش هزینه هر تحویل موفق، شامل retryها.
4. آزمایش migration روی شاخه جداگانه Neon با داده مشابه تولید و برنامه rollback، سپس بررسی دستی پیش از هر انتشار. Production در این اسپرینت بدون تأیید مالک تغییر نمی‌کند.

## Migration / بازگشت

`0008_usage_cost_estimates.sql` فقط ستون‌های nullable و یک index اضافه می‌کند؛ داده‌های پیشین تغییر نمی‌کنند. بازگشت کامل پس از بازگرداندن کد قبلی و تهیه نسخه پشتیبان: حذف index `usage_records_reservation_idx` و ستون‌های `reservation_id`, `run_id`, `agent_role`, `gateway`, `estimated_cost_toman`, `tariff_snapshot` از `usage_records` با migration معکوس مدیریت‌شده. حذف ستون‌ها برآوردهای ثبت‌شده را از بین می‌برد. journal نیز باید با روش مهاجرت همین پروژه مدیریت شود؛ rollback روی Production بدون بررسی و تأیید اجرا نشود.

## کنترل پولی در شاخهٔ اسپرینت (نیازمند بررسی پیش از انتشار)

Migration 0009 تابع اتمیک `reserve_ai_money` را اضافه می‌کند. پذیرش کلید پلتفرم تحت قفل تراکنشی مشترک، سقف‌های غلتان ۲۴ ساعت و ۳۰ روز برای پلتفرم، کاربر و پروژه و سقف کل اجرا را بررسی می‌کند. سقف‌های `common` و `free` باید در `AI_TOMAN_LIMITS_JSON` با عدد صحیح تومان و توسط مدیر پیکربندی شوند. سقف مشترک پلتفرم برای همه یکسان است؛ برای سایر موارد محدودیت حساب رایگان کمینه دو مقدار است. تنظیمات ناقص، نرخ مدیر قدیمی/نامعتبر، تصویر یا gateway نامعتبر درخواست پلتفرم را متوقف می‌کند. کلید شخصی همچنان محدودیت توکن اجرای موجود را دارد و هزینهٔ مالی کلید پلتفرم را مصرف نمی‌کند.

رزرو تا جای ممکن محافظه‌کارانه است: همه توکن‌های برآوردی به بالاترین نرخ ورودی/خروجی و ۴۰۹۶ توکن سربار محاسبه می‌شوند. پس از پاسخ، رزرو کاهش نمی‌یابد و در صورت بالاتر بودن برآورد مصرف واقعی افزایش می‌یابد. timeout یا خروجی بدون داده مصرف رزرو را نگه می‌دارد. این روش نمی‌تواند صورتحساب نهایی، دسته‌های قیمت‌گذاری خاص یا سربار غیرقابل‌پیش‌بینی ارائه‌دهنده را تضمین کند؛ صورت‌حساب باید جداگانه تطبیق داده شود.

مصرف پلتفرم قبلی در ۳۰ روز گذشته که به رزرو تومانی قابل اتکا وصل نیست، پذیرش جدید را مسدود می‌کند؛ آن را با عدد صفر یا تنظیم دوباره ساعت دور نزنید. پیش از انتشار باید برنامه تطبیق هزینه تاریخی، جریان ارتباط به مشتریان، نرخ‌های دقیق، و آزمایش migration و رقابت روی PostgreSQL واقعی تدوین شود. تا تکمیل این موارد و آزمایش جریان‌های پولی، این تغییر آماده Production نیست. کنترل تعداد و هزینه Build و گزارش هزینه تحویل موفق هنوز پیاده نشده‌اند.

برای rollback، ابتدا کد سازگار قبلی را بازگردانید؛ پس از پشتیبان و ارزیابی داده‌ها، در migration معکوس مدیریت‌شده تابع `reserve_ai_money`، ایندکس `usage_reservations_cost_idx` و ستون‌های `project_id` و `reserved_toman` جدول `usage_reservations` حذف شوند. حذف این ستون‌ها رد رزروهای مالی را از بین می‌برد؛ اجرای rollback در Production به تأیید مالک نیاز دارد.

## سهمیه Build رایگان (در شاخه و پیش از تأیید انتشار)

Migration 0010 پذیرش‌های Build را ثبت می‌کند. برای حساب رایگان، پیش از push و dispatch اپ موبایل، تابع اتمیک با قفل سطر کاربر سقف `FREE_BUILDS_PER_30_DAYS` را بررسی می‌کند؛ Buildهای قدیمی بدون پذیرش لینک‌شده هم شمارش می‌شوند. مقدار باید صریحاً توسط مدیر تعیین شود؛ مقدار صفر تمامی ساخت‌های رایگان موبایل را متوقف می‌کند. وب و اشتراک‌های پولی با این سیاست محدود نمی‌شوند. تلاش نامطمئن به‌صورت محافظه‌کارانه باقی می‌ماند؛ خطای اتصال در میانه کار ممکن است به بررسی پشتیبانی نیاز داشته باشد. این سهمیه صرفاً تعداد تلاش است و صورتحساب GitHub یا هزینه مالی واقعی را تعیین نمی‌کند. GitHub می‌تواند از سهمیه رایگان یا تعرفه حساب صاحب مخزن استفاده کند؛ بدون صورت‌حساب منتسب، مبلغ واقعی نامشخص است.

بازگشت 0010 پس از بازگرداندن کد و تهیه نسخه پشتیبان: تابع `admit_free_build` و جدول `build_admissions` با migration معکوس مدیریت‌شده حذف شوند؛ این کار تاریخچه پذیرش را از بین می‌برد. Production بدون تأیید و آزمایش داده مشابه آن تغییر نکند.

## مشاهده Build و هزینه نامعلوم

Migration 0011 به `build_jobs` شماره تلاش، زمان شروع و آخرین تغییر گزارش‌شده GitHub و فاصله زمانی مشاهده‌شده برای اجرای پایان‌یافته را اضافه می‌کند. فاصله بین `run_started_at` و `updated_at` تخمین زمان سپری‌شده در سطح workflow است؛ زمان قابل‌صورتحساب runner، مجموع اجرای jobهای موازی یا مبلغ صورتحساب نیست. ستون‌های مبلغ و منبع و تاریخ هزینه nullable هستند و تا تطبیق با شواهد صورتحساب خالی می‌مانند؛ مقدار صفر به عنوان پیش‌فرض ذخیره نمی‌شود. داده‌های Build قبلی نیز نامعلوم باقی می‌مانند.

بازگشت 0011 پس از بازگرداندن برنامه و تهیه نسخه پشتیبان، با migration معکوس مدیریت‌شده و حذف ستون‌های `run_attempt`, `run_started_at`, `run_updated_at`, `reported_elapsed_seconds`, `cost_toman`, `cost_source`, `cost_recorded_at` است. این حذف اطلاعات بعدی را از بین می‌برد. هنوز سازوکار واردکردن/تطبیق امن صورتحساب و گزارش هزینه هر تحویل موفق پیاده نشده است.
